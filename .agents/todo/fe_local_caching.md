#Tài liệu kỹ thuật: Triển khai Local Caching kết hợp Tenant Metadata & Realtime Sync Tài liệu này mô tả kiến trúc caching dữ liệu dưới local (LocalStorage/IndexedDB) cho các danh mục ít thay đổi (như tag, danh sách nhân viên) áp dụng chiến lược **Lazy Loading (On-demand)**, **Tenant-based Versioning**, và **Request Deduping** để tối ưu hóa hiệu năng và băng thông. --- ## 1. Kiến trúc tổng quan * **Single Source of Truth cho Version:** Thông tin `last_updated_at` (hoặc `version`) của các danh mục được đính kèm trực tiếp trong thông tin **Tenant** (được trả về và lưu trữ khi người dùng đăng nhập). * **Lazy Loading:** Không tải dữ liệu ngầm ngay khi đăng nhập. Dữ liệu chỉ được fetch khi component có nhu cầu hiển thị lần đầu hoặc khi phát hiện cache cũ. * **Request Deduping:** Gom nhóm các request gọi đồng thời (tránh tình trạng nhiều component cùng gọi `getTags()` gây trùng lặp request API). * **Realtime Update (Socket):** Khi có thay đổi từ server đẩy xuống qua WebSocket, tiến hành cập nhật lại `last_updated_at` trong state của Tenant (hoặc xóa cache), không bắt buộc phải fetch lại ngay lập tức mà để cơ chế Lazy Loading tự xử lý ở lần truy cập tiếp theo. --- ## 2. Luồng xử lý (Workflow) 1. **Khi User Đăng nhập:** * Lấy thông tin `Tenant` (chứa các mốc thời gian cập nhật, ví dụ: `tenant.config_metadata.tags.last_updated_at`). * Lưu `tenant` state vào bộ nhớ ứng dụng. 2. **Khi Component cần dùng dữ liệu (Ví dụ: `getTags()`):** * **Bước 1:** Kiểm tra local cache (`localStorage` / `IndexedDB`). * **Bước 2:** So sánh `local_cache.last_updated_at` với `tenant.config_metadata.tags.last_updated_at`. * **Bước 3:** * Nếu khớp $\rightarrow$ Trả về dữ liệu từ local cache ngay lập tức (0ms). * Nếu lệch/chưa có $\rightarrow$ Kiểm tra xem có đang có request nào đang chạy ngầm hay không (Request Deduping). Nếu có, dùng chung Promise; nếu không, gọi API lấy dữ liệu mới, lưu đè vào local cache kèm `last_updated_at` mới và trả về dữ liệu. 3. **Khi nhận sự kiện qua Socket:** * Nhận event cập nhật (ví dụ: `tag_updated`, kèm `new_last_updated_at`). * Cập nhật lại giá trị tương ứng trong `tenant.config_metadata`. --- ## 3. Đoạn mã mẫu triển khai (JavaScript/TypeScript) ```javascript // Biến giữ chỗ phục vụ Request Deduping let pendingTagsPromise = null; /** * Hàm lấy danh sách Tag theo cơ chế Lazy Loading + Caching + Deduping */ async function getTags() { const CACHE_KEY = 'tags_cache'; // 1. Đọc cache từ Local Storage const rawCache = localStorage.getItem(CACHE_KEY); const parsedCache = rawCache ? JSON.parse(rawCache) : null; // 2. Lấy metadata từ Tenant (đã lưu lúc đăng nhập) const tenantMeta = getTenantMetadata(); // { tags_updated_at: number } const serverVersion = tenantMeta?.tags_updated_at || 0; // 3. Kiểm tra tính hợp lệ của cache const isCacheValid = parsedCache && (parsedCache.last_updated_at === serverVersion); if (isCacheValid) { return parsedCache.data; // Dùng cache local } // 4. Chống xung đột request trùng lặp (Request Deduping) if (pendingTagsPromise) { return pendingTagsPromise; } // 5. Fetch mới từ Server nếu cache out-of-date hoặc chưa có pendingTagsPromise = (async () => { try { const freshData = await api.fetchTags(); // Gọi API thực tế // Lưu vào local cache kèm version mới từ tenant localStorage.setItem(CACHE_KEY, JSON.stringify({ last_updated_at: serverVersion, data: freshData })); return freshData; } finally { // Reset promise sau khi hoàn tất (dù thành công hay lỗi) pendingTagsPromise = null; } })(); return pendingTagsPromise; } 
4. Các lưu ý quan trọng dành cho AI khi phát triển/bảo trì
• Trường hợp Clear Cache / Trình duyệt ẩn danh (Incognito):
◦ Biến localStorage có thể bị xóa bất cứ lúc nào. Hàm lấy dữ liệu luôn phải có cơ chế fallback an toàn (nếu localStorage.getItem trả về null thì tự động coi như cache không hợp lệ và gọi API).
• Đồng bộ hóa State Tenant khi có Socket:
◦ Khi nhận event Socket (ví dụ: tag_changed), bắt buộc phải cập nhật lại biến tenant.config_metadata.tags.last_updated_at trên memory client. Nếu không cập nhật state này, client sẽ tiếp tục dùng cache cũ do thấy version vẫn khớp.
• Tách bạch Metadata theo từng module:
◦ Không dùng chung một mốc last_updated_at cho toàn bộ các bảng. Mỗi danh mục (Tags, Employees, Categories...) phải có một key thời gian riêng biệt trong config_metadata để tránh việc một thay đổi nhỏ ở Tag lại ép hệ thống phải đi kiểm tra/làm mới toàn bộ danh sách Nhân viên.
• Xử lý ngoại lệ (Error Handling khi gọi API):
◦ Nếu gọi API lấy dữ liệu mới thất bại (mất mạng), cân nhắc việc có nên tạm thời fallback về cache cũ kèm theo thông báo cảnh báo (Stale-while-error) thay vì làm sập ứng dụng.
